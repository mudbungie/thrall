## What happens

A tool that starts a background helper and then exits leaves the invocation
unanswered **forever**, and wedges the whole channel behind it.

Driven with a tool whose whole body is:

    sh -c 'sleep 3600' &
    echo "helper=$!"
    exit 0

The tool exits in well under a second. Observed: no capture after 25 s; a
second invocation posted afterwards also never completes; the foot process is
healthy with no children; `thrall` has two threads parked in `anon_pipe_read`
and the main thread in `futex_do_wait`. The helper's fd 1 and fd 2 are the
**same two pipe inodes** thrall's own read ends point at. Signalling the helper
released both drains and BOTH captures landed at once, in order.

## Why

`exec::run` bounds only the child's own exit. `waited(&mut child, deadline)`
returns the moment `try_wait` reports the tool gone — and everything after it is
unbounded:

    let (exit_code, note) = waited(&mut child, deadline);
    if let Some(feeding) = feeding { let _ = feeding.join(); }
    let mut stderr = out_of(err);
    ...
    Ok(captured(&out_of(out), &stderr, exit_code))

`out_of` joins a thread doing `read_to_end` on the pipe. A pipe read ends when
**every** writer closes, and the helper inherited the write end. So the deadline
governs the process thrall started and not the pipe it is reading, which are
different things whenever a tool backgrounds anything.

## Why it matters

- Backgrounding is ordinary in tool scripts — starting a daemon, a build
  server, anything with `&` or `nohup`.
- The loop is serial per channel, so the wedge is the channel's, not the
  invocation's: everything queued behind it stops too.
- A foot never reconnects by design, so nothing recovers it short of restarting
  the process — and the restart loses the in-flight invocation outright.
- The engine reads an absent capture as *the far machine is still running it*,
  so the asking side waits out the full slot TTL on a tool that finished.

## Against the design

`exec.rs`'s own module doc states the property this breaks:

> **Every outcome is a capture.** ... because an invocation that earned no
> answer would be the hang the whole leg exists to exclude

and DESIGN §3.5 lists the deadline as one of the three things thrall enforces
locally. Neither is true while a descendant holds the pipe.

DESIGN §3.5 does say a tool finishing inside its deadline is not signalled and
whatever it left running is left running — that part is honoured and is not the
complaint. The complaint is that thrall then never answers.

## Shape of a fix (not prescribing)

The deadline should bound the whole capture, not the child's exit — the drain
joins need the same clock. The three candidate shapes are: give the child's
stdio pipes to the child only (so a descendant that wants to outlive it must be
given its own), bound the drain and report what was read, or treat the deadline
as a wall for the invocation rather than for the process.

## Repro

Config entry pointing `command` at the three-line script above; invoke it; poll
for the capture; then post a second invocation and watch it queue.
