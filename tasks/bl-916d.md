**Filed from the engine side** while closing yog bl-0a74, which asked for this
loop inside yog. It cannot land there: the client half of the wire — the dialler,
the per-channel fan-out, the whole `wire/host/` family bl-0a74 names by path — was
deleted from yog at the severance, and this crate is where it lives now. The
engine's half of bl-0a74 has landed as doc: yog REMOTE §5.3 and §5.1, below.

## The gap

`run::fan` starts one thread per entry and `run::hold` serves it until a gesture
fails, at which point it returns the sentence that failed it and that channel is
over for the life of the process. `channel.rs` and `run.rs` both state the ruling
plainly — *"It never reconnects. A channel that fails is the sentence that failed
it, handed back. Restart policy belongs to the supervision the operator's machine
already has."*

That is the right error model and the wrong lifetime model for the roaming box
yog REMOTE §1 calls canonical. A laptop that sleeps, changes network or crosses a
relay switch drops TCP; the thread ends cleanly; and from then until somebody
restarts the process, the engine believes this box is gone (presence is connection
RAM, correctly) while the box sits there believing it is serving. The operator's
symptom is tools that silently stopped being offered by a live-looking process.

**The premise is sound and the conclusion does not follow: supervision restarts a
process, and this failure does not kill one.** A multi-entry box loses one channel
of several and keeps serving the rest, so there is no exit code for a supervisor to
see. A single-entry box does exit — and that arm stays exactly as it is.

## The ruling that forbade it has been reversed upstream

yog REMOTE §5.3 previously read *"it does not reconnect ... inventing one here
would be yog deciding how a box it does not administer runs a program"*, which is
the sentence both files here quote. That paragraph now reverses the ruling **at
the channel and keeps it at the process**: a foot redials its own channels, and
still exits when it cannot be a foot at all. So this is no longer a deviation from
the protocol doc; implementing it without the redial now is.

## Shape

A redial loop with backoff around each channel's thread — `fan` already owns the
per-channel lifetime, so the loop belongs between `entry.open()` and `hold`, not
inside `hold`. The channel dies, the loop waits, the entry is opened again, and
presence re-forms on the engine side exactly as a fresh connection would.

Nothing protocol-side changes: the advertisement rides the connection already
(`hold` presents first thing), registration is durable engine-side, and the
invocation mailbox tolerates a consumer coming and going — an invocation in flight
when the wire died is the mailbox's lease, not the redial's.

**It must not become a session resume**: there is nothing to resume, and presence
is deliberately ephemeral. **It must not spin**: a box in airplane mode settles to
a slow cadence rather than burning a core.

## The one refusal it MUST treat as retryable, or it defeats its own purpose

yog REMOTE §5.1's one-reader guard refuses a second concurrent `invocations` read
under one identity, naming the client. A read parked when its connection died does
not leave until the engine tries to answer it, so **a redial inside that window is
refused naming this very machine** — the stale predecessor, not a rival.

It is bounded, and yog now states the bound as a contract rather than an accident:
*"Its life is the hold and not the connection's ... `Mailbox::take` drops the claim
on the way out, before the caller writes the answer, so a peer that vanished without
a FIN frees the slot within one hold's width — thirty seconds."*

So: wait past one hold's width and ask again. A redial loop that took that sentence
as final would make the first network blip permanent, which is the defect this ball
exists to fix.

**A refusal from the ADVERTISE guard is a different animal and must still stop the
channel** (bl-2d78's own settlement): that one means another connection holds this
machine's read with a different set in force. Two refusals, two answers — do not
collapse them into one retry.

## Interaction with the two balls already open

- yog bl-66d4 puts a `stored` field on the `advertised` reply, so a re-presentation
  that actually restored a blanked set says so. A redial re-presents on every new
  connection, which makes it a coarser instance of the same self-heal — a `true`
  arriving on a redial's presentation is this machine learning it was disarmed.
- bl-e834 (a dead channel's sentence is buffered until every channel stops) gets
  worse under a redial, not better: with a loop in place a channel's sentence is
  no longer terminal, so it has to reach the operator as it happens or not at all.
