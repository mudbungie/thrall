**Engine-side, filed here because it was found driving the foot and the foot is
the party that is silently disarmed.**

## What happens

The advertised set is engine-side state keyed on the client identity, and it is
last-writer-wins. Any connection bearing that identity can replace it — and the
foot that is running never finds out.

Observed: a running foot serving normally; a second, separate connection using
the same leaf sent `{"op":"advertise","tools":[]}` and was answered
`{"kind":"advertised","ok":true}`. From then on every invoke for that client was
refused engine-side with

    client "<name>" advertises no tool "<tool>" right now

while the foot sat there healthy, connected, and holding a document full of
tools. Restarting the foot restored the set, because presenting happens on
connect.

## Why the foot cannot notice

By design, and the design is stated:

> **The advertisement is presented once per channel, not once per dial.** ...
> the far end writes the set only when it differs from what is stored, so
> re-presenting costs nothing, while re-presenting before *every* read would
> double the traffic to say a thing that had not changed.

That reasoning is sound for traffic. What it assumes is that nothing else
writes the set. Nothing in the protocol makes that true, and there is no
version, no generation and no receipt on the read that would let a foot detect
that the set it presented is not the set in force.

## How real is it

Modest, and worth saying plainly: it takes a leaf that the operator minted, so
this is not a stranger's reach. The realistic shapes are a copied entry
directory, the same box provisioned twice, or a foot restarted while an old
process is still up. In each the failure is silent on both ends — the engine
believes the box offers nothing, the box believes it is serving, and the only
symptom is invocations refused for a tool that plainly exists.

## What would be enough

Not a per-request re-advertisement. Either the set carries the identity of the
connection that wrote it, or the follow-class read's answer says which set is
in force, so a foot whose set has been replaced learns it on its next read
rather than never.

## Repro

Run a foot. From a second connection with the same leaf, send an `advertise`
carrying the empty array. Invoke any tool: refused. The foot logs nothing and
keeps waiting.
