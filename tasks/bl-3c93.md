## Two defects, one line of code

`exec::run` formats every spawn failure against the command:

    let mut child = crate::spawn::spawn(&mut cmd).map_err(|e| format!("{head}: {e}"))?;

`head` is the argv's program. But the spawn can also fail because of `cwd`, and
then the sentence names the wrong thing entirely.

### 1. A bad `cwd` is reported as a missing command

A tool entry whose `command` exists and is executable, and whose `cwd` names a
directory that does not exist, earns:

    thrall: <path to the command>: No such file or directory (os error 2)

The command is fine. The directory is the problem, and nothing in the sentence
says so — an operator reads it as a broken `command` and goes looking at a file
that is exactly right. The function's own doc comment already knows the class:

> The `Err` is a fork that never happened — an argv with no program in it, a
> missing binary, **an unusable working directory** — which is the one outcome
> that is not the child's own verdict.

Three causes, one spelling, and the spelling names one of them.

### 2. A relative `cwd` is silently resolved against the process's own directory

An entry with `"cwd": "relative/dir"` is accepted at read time and runs the tool
in `<wherever thrall was started>/relative/dir`. Confirmed: creating that
directory beside the foot's working directory made the tool run there, with no
sign anywhere that a relative path had been resolved against anything.

This is precisely the hazard `paths.rs` refuses for the data root, in writing:

> **Neither variable set is a refusal, not a guess.** A relative fallback would
> put an operator's certificates wherever the supervisor happened to start the
> process, which is a place nobody chose and nobody can find again.

The tool document is the same kind of operator-authored fact, read on the same
box, and it takes a relative path without comment. Where a tool runs then
depends on the supervisor's working directory — a fact no one wrote down and
that changes when the unit file does.

## Why one ball

Both are the same missing read of `cwd`. `config::read` already refuses a set it
cannot address (an unusable name, a duplicate name, an empty argv) at the read
rather than at the first invocation, for the stated reason that an operator
should learn about a bad document when the document is read. A `cwd` that is not
absolute belongs in that same check; a `cwd` that does not exist belongs either
there or in a spawn error that names it.

## Repro

Two entries with the same working `command`: one with `"cwd": "relative/dir"`,
one with `"cwd"` naming an absent absolute directory. Invoke each.
