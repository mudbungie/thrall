What to build (yog docs/REMOTE.md section 5.7: 'A capture is N >= 1 posts' and the rule 'A run lives while its asker listens'). When the server's hello states an edition at or above the stamps of request/complete `partial`, post `{op: complete, invocation, partial: {stdout, stderr}}` whenever the child has written something or ten seconds have passed, whichever is first, cut on character boundaries; the final post carries `capture` with the exit code and only the text not yet posted. Hold one connection for the posts of a run. A post refused in band terminates the child through the existing cascade, drops the run and reads on (never Over). A post that cannot reach the server is retried within a short bound, then the child is terminated and the channel redials. For a streaming run the fixed two-minute child deadline no longer applies: the asker's listening is the bound. The capture limit bounds one post, not the run. To a server of an older edition behave exactly as today: one post, the two-minute deadline, the per-run limit. The held-capture re-post (a completion the wire swallowed) is unchanged for the final post. Every tool streams; there is no per-entry key. Amend this repository's DESIGN where it states the single post, the deadline and the limit.

Tested by: src/run and src/exec tests with literal frames: a slow child's first line is posted before it exits; a silent child posts an empty partial at the cadence; a refused post kills the child's process group and the channel takes its next invocation; an older edition gets one post; posts concatenate to exactly the child's output across a multi-byte boundary; the corpus replay covers the new paths once vendored.
