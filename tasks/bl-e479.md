The macOS half of the containerized-build ruling (yog bl-888d, under yog DESIGN
Section 10 and 10.1). Today the Linux image comes off a reproducible container line and
a mac binary would come off somebody's laptop. It should come off the same line.

The deliverable: a build-only `Containerfile.mac` and a `make mac-artifact`
target that cross-produces the `aarch64-apple-darwin` binary from a Linux
container, plus a verifier that reads the produced Mach-O rather than trusting
the build, and a README section stating what is proven and what is not.

THE TOOLCHAIN IS zig cc (cargo-zigbuild), and osxcross is refused. osxcross
needs the Apple SDK, which the Xcode and Apple SDKs Agreement forbids on two
independent grounds: section 2.7 ("You agree not to ... upload to or host on any website
or server, sell, redistribute, or sublicense the Apple Software ... or to enable
others to do so") means the SDK may never sit in this repo or in any layer we
publish, and section 2.5 ("You are expressly prohibited from separately using the
Apple SDKs or attempting to run any part of the Apple Software on
non-Apple-branded hardware") means an operator-supplied SDK on a Linux builder
is outside the grant too. So it is not a case of holding the SDK at arm's
length; the whole arm is refused. zig ships one darwin stub of its own
(`lib/libc/darwin/libSystem.tbd`) under its own licence, acquires nothing from
Apple and asks nobody to accept an Apple agreement.

THE LIMIT THAT FOLLOWS, and it is why thrall is the component this lands in:
zig ships libSystem and NO framework stubs at all. A crate graph that links
only libSystem crosses; one that links any Apple framework does not, and there
is no lawful way to supply the frameworks on a Linux builder. thrall links
none - its dependency set is rustls/ring and serde_json over std - so its mac
artifact is producible here and the seat's and the engine's are not.

WHAT MUST BE PROVEN, not asserted. No mac exists on the build box, so the
artifact cannot be executed. It can still be read: the Mach-O header (magic,
cputype arm64, filetype MH_EXECUTE), LC_BUILD_VERSION (platform, minimum OS)
and every LC_LOAD_DYLIB. A verifier that reads those out of the file is the
evidence; "the build succeeded" is not. Record the macOS floor the artifact
actually carries rather than the one the linker was asked for - the pinned zig
sets it and the request is ignored.

Pins, because reproducibility is the point: the zig tarball by version AND
sha256, cargo-zigbuild by exact version with `--locked`, the rust toolchain by
the same digest-pinned base image and the same drift check the Linux
Containerfile already runs against `rust-toolchain.toml`.

The build image is a fixture and is never pushed, so `make image-scan` does not
apply to it; the artifact's content is compiled from the tree the source gate
already reads, exactly as the Linux release binary is.
