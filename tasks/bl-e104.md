Child 1 of the MCP bridge design (DESIGN §6, bl-3b03). One lane-day.

CONTRACT

A new subcommand, `thrall mcp <tool> -- <server argv...>`, is an ordinary tool
command under the tool document's existing stdin/stdout/exit-code contract
(README "The tool document"; DESIGN §3.4). A pinned MCP tool is therefore an
entry whose `command` begins with the thrall binary, e.g.

    {"name": "fetch", "description": "...", "input_schema": {...},
     "command": ["/usr/local/bin/thrall", "mcp", "fetch", "--", "uvx", "mcp-server-fetch"]}

and the document gains NO key: `config::read`, the advertisement and `exec`
are untouched, and deleting the entry deletes the capability (§3.4).

What one invocation does, in order:
1. read the invocation's `input` JSON from stdin — the whole object, verbatim;
2. spawn `<server argv>` through the spawn boundary (`spawn::spawn` — own
   process group, git scrub), stdin/stdout piped, stderr inherited;
3. speak MCP's stdio transport — newline-delimited JSON-RPC 2.0 —
   `initialize` (protocolVersion "2025-06-18", capabilities {}, clientInfo
   {name: "thrall", version: crate version}), `notifications/initialized`,
   then exactly one `tools/call {name: <tool>, arguments: <input>}`;
4. render the result to stdout (below); exit; tear the server down — close its
   stdin, wait briefly, then signal its group (`sys::kill_group`, the cascade
   `exec::child` already owns). The server's lifetime is contained in the
   invocation's (DESIGN §6.4): no resident server, no reconnect, and the
   serial-per-channel rule (§2) is untouched.

Rendering (DESIGN §6.5):
- `content` text parts are written to stdout in order, each followed by a
  newline;
- a non-text part (image, audio, resource) is replaced by ONE line naming its
  type, mime type and byte length, e.g. `[image image/png, 48213 bytes dropped]`
  — a capture is text (yog REMOTE §5.3) and the bytes are not carried;
- `structuredContent`, when present and no text part is, is written as the
  JSON it is;
- `isError: true` → the content is still written, exit 1;
- a transport or protocol failure (server would not start, no `initialize`
  answer, a JSON-RPC error on the call, an unparseable frame) → one sentence on
  stderr naming the stage and the server's first argv word, exit 1. Never the
  server's environment, never the full argv (DESIGN §6.7: a spawn failure loves
  to quote the command line, and the bridge must not).

Tests: a fake MCP server as an executable fixture (written by a child through
`test_support::write_exec`, never `fs::write` — the ETXTBSY rule) that speaks
the three messages and answers a canned `tools/call`; one test per rendering
row above; one for teardown (the fixture's group is gone after the capture);
one driving it through `exec::execute` as an entry of a real document, so the
bridge is proven as a tool command and not only as a function.

Module map rows (DESIGN §4): `src/mcp.rs` (the verb: input in, capture out),
`src/mcp/rpc.rs` (the framing and the three requests), `src/mcp/render.rs`
(content parts to bytes). Pre-split: none may project past 200 lines.

No new dependency: `serde_json` is already linked, and the codec is the
hand-written strict-field style `src/json.rs` establishes.

Refusals carried from DESIGN §6.8: no HTTP or SSE transport; no `mcp` key in
the document; no generic `{server, tool, arguments}` passthrough — one entry
per tool, the load act on the far end names one.
