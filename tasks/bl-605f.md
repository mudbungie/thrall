bl-6c98 shipped `make deploy-local`, which seats the box it is run on. There is
no remote form, so a foot can only be deployed by a human logged in to the box
that will run it — which is exactly backwards for the box class that most needs
one. lernie's `scripts/deploy/seat.sh` carries the shape to copy since its
bl-bae7: ONE payload, two carriers, `put`/`run` the only things a HOST changes,
so a local and a remote seating cannot drift.

The live gap this was found in. A deployment of this suite currently runs the
engine on an always-on server box and the foot on a laptop, and the server's
engine holds a foot certificate issued for the laptop. That means:

  * the server can execute nothing while the laptop is asleep, off, or on
    another network — which for a laptop is most of the time;
  * the server can never execute anything ON ITSELF, so an agent asked to look
    at the box it is running on has no way to;
  * neither end says so. REMOTE §5.1 stores one advertised set per identity and
    DESIGN §3.7 rules that a working foot is ABSENT from the engine's view, so
    a foot that is not running looks like a foot that has not spoken lately, and
    the engine cannot probe (§3.1 forbids it speaking first).

The server box has no `thrall` binary, no unit and no data root at all. The act
is three things and only the first is code: a remote carrier here, an
operator-issued foot certificate for that box, and a `tools.json` saying what
the box offers.

Blocked behind bl-f88f: this crate speaks PROTOCOL 8 and a current engine speaks
13, so a foot seated on that box today would redial forever without opening a
channel (bl-5d62). Seat it after the pin lands and a release publishes.
