Observed live on the first armed run of the release pipeline (bl-bbb3), which
is the best evidence this kind of gap ever gets.

`.github/workflows/release-plz.yml`, `prune-release-branches`:

    needs: release-plz-pr

and its own comment states the case it exists for:

    release-plz pushes a NEW timestamped `release-plz-*` branch each time it
    refreshes the release PR, and pushes it BEFORE opening the PR, so
    superseded and orphaned branches pile up one per push to `main`

Read those together and they disagree. release-plz pushes the branch FIRST and
opens the PR SECOND, so the window in which a branch exists with no PR is
exactly the window in which the PR step can still fail — and a `needs:` edge
with no `if:` means a failed `release-plz-pr` SKIPS the collector. The job
runs on every path except the one that creates the orphan it names.

WHAT HAPPENED. The first armed run pushed `release-plz-<timestamp>` and then
403d opening the PR (the repository setting was not yet enabled). prune was
skipped; the branch was left with no PR and nothing to ever close it, and was
deleted by hand. The `no open PR` test the job already uses would have
collected it correctly had the job run at all.

THE FIX IS ONE LINE and the shape is already in the file elsewhere: run the
collector whenever the PR job RAN, rather than only when it succeeded --
`if: always()` (or `!cancelled()`) beside the `needs:`, which keeps the
ordering the job depends on (the current PR is already open, so `has no open
PR` stays an exact test) while dropping the implicit `success()`. Check what
that does to the dispatch path, where `release-plz-pr` is skipped rather than
failed and the collector should still stay skipped.

THE SIBLING REPOSITORIES CARRY THE SAME SHAPE, so this is a suite-wide note
and not a thrall defect -- the file was ported. Whoever fixes it here should
say so wherever the pattern is mirrored.
